6502 Microprocessor Emulator

A C++ implementation of the 6502 CPU core built to understand how opcodes, addressing modes, memory, timing, flags, the stack, and interrupts cooperate during instruction execution.

01 / Problem

Why I built it

High-level programs hide the work performed between an instruction and a result. I wanted to make that path concrete by implementing the processor state and execution loop myself.

02 / Design

System shape

The CPU owns registers, status flags, the stack pointer, program counter, cycle state, and a connection to memory. Each opcode selects an operation and an addressing mode; both contribute to the final cycle count. The wider repository now contains NES components, but this case study focuses on the 6502 layer that began the project.

03 / Implementation

What the code actually does

  • 01

    Registers, status flags, program counter, stack pointer, and memory reads/writes

  • 02

    Instruction decoding through opcode, operation, and addressing-mode tables

  • 03

    Stack operations, branches, arithmetic and logical operations, and page-crossing behavior

  • 04

    Reset, non-maskable interrupt, and interrupt-request handling

  • 05

    Cycle-aware stepping that allows execution state to be inspected incrementally

04 / Decisions

Engineering choices

01

Separate operation from addressing

Keeping the instruction behavior separate from the way its operand is located reduced duplication and made the execution table easier to reason about.

02

Model state explicitly

Registers and flags remain visible values rather than being hidden behind a generic execution function, which makes debugging closer to reading a processor trace.

03

Preserve timing information

Tracking cycles made the emulator more than an opcode calculator and prepared the CPU core for integration with other timed components.

NMI + IRQ

Observed while building

  • The same instruction can require different work depending on its addressing mode.
  • Interrupts are state transitions with strict stack and flag behavior, not ordinary function calls.
  • Small mistakes in flags or program-counter movement propagate into failures many instructions later.

Next iteration

Continue validating CPU behavior inside the broader NES integration and improve automated instruction-level testing.
